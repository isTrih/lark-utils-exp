# 星图自动化项目工程化复盘

## 关键词核心要点

| 关键词 | 核心要点 |
| --- | --- |
| 观察先行 | 先用浏览器插件采集真实网络、控制台、窗口跳转、点击和请求关系，再决定后端怎么做。 |
| 证据驱动 | 通过 NDJSON 日志证明星图任务导出、长任务轮询、飞书表格链接返回链路可行，避免凭经验猜接口。 |
| 双路径设计 | 官方异步导出是主链路，分页 JSON 拉取是备用/增强链路，降低平台策略或下载链路失败带来的风险。 |
| 登录态工程化 | 把 Cookie、CSRF、session_key、User-Agent 作为系统输入，提供插件上报、`.env` 导出、后端保存和巡检。 |
| 模块化 Pipeline | 从 006 的视频同步试验，逐步拆成可配置的直播/视频同步、手动合并、入库、同步飞书、审核通知流程。 |
| 配置外置 | 每期活动变化的 bitable、table、任务、审核、通知配置全部抽到 JSON/数据库，工作流代码保持稳定。 |
| 数据先入库 | 同步前先把星图和手动登记数据规范化入 PostgreSQL，再同步到多维表，后续查询、追踪和补偿都有依据。 |
| 幂等补偿 | pending 飞书来源、批量 upsert、定时导入和手动补偿接口，让失败任务可以重跑而不破坏已有数据。 |
| 定时工作流 | 落地每日 03:00/15:00/21:00 周期同步、09:00 审核同步、23:59 最终同步，以及登录态小时级巡检。 |
| 可观测与文档 | 提供 HTTP API 文档、Swagger/OpenAPI、Docker 部署文档、查询接口和分析接口，让系统可运营、可交接。 |

## 总览

这个项目不是一开始就直接写“自动化后端”，而是按工程化节奏逐步收敛：

1. 先采集真实操作证据。
2. 再逆向验证关键接口链路。
3. 做一个最小 Rust/Salvo 工具验证任务 ID 到飞书表格链接。
4. 用插件解决登录态来源问题。
5. 把一次性测试程序整理成可配置 pipeline。
6. 建数据库模型和定时工作流。
7. 服务化、文档化、容器化、发布。
8. 最后补上数据查询和分析接口，服务前端或运营后台。

这条路径的关键价值是：每一步都只承担当前阶段最重要的不确定性，验证通过后再进入下一层工程化。

## 阶段一：先做调试采集器，而不是直接写自动化

项目的第一个前置工作是 `xingtu.cn` 调试采集插件。

当时的问题是：星图页面每天都需要人工操作，但还不清楚哪些接口真正可复现、哪些请求依赖浏览器状态、哪些按钮会打开新窗口。直接写后端风险很高，因为会遇到登录态、SSO、异步导出、风控和字段不完整等未知问题。

所以第一步选择做浏览器插件，用最小侵入方式记录：

- `xingtu.cn` 和 `sso.oceanengine.com` 的网络请求。
- 控制台输出。
- `fetch`、`XHR`、`webRequest` 三类请求。
- 新窗口、新标签页、`openerTabId`、`windowId`、`tabId`。
- `window.open()` 调用。
- 后续补充的飞书 wiki 页面点击、鼠标位置、疑似单元格、点击后触发的请求关系。

日志格式选择 `NDJSON`，因为它适合持续追加、失败恢复、按行读取，也方便 AI 后续分析。

这个阶段体现的工程化判断是：先建立可观测性，不急于实现业务逻辑。只有先看到真实链路，后面的系统才不会建立在猜测上。

## 阶段二：把日志变成可执行判断

第二个前置工作是分析采集日志，逆向接口并判断能否自动化。

第一次日志证明了这些接口关系：

- 任务列表接口可以拿到 `task_id`。
- 投稿列表接口 `demander_get_challenge_item_list` 可以通过 `challenge_id={task_id}` 分页拉数据。
- 官方导出接口 `download_demander_challenge_item_list` 会返回 `ticket_id`。
- 长任务接口 `get_long_task_result` 用 `ticket_id` 轮询导出结果。

同时也发现风险：当时长任务返回过“不支持下载，境外 IP 地址登陆不支持下载功能”。这说明官方导出链路受网络环境和登录策略影响。

后来新版日志补齐了关键证据：

- `download_demander_challenge_item_list` 成功返回 `ticket_id`。
- `get_long_task_result` 从 `status = 2` 轮询到 `status = 3`。
- `result` 字段里返回了飞书电子表格链接。
- `result` 是字符串形式 JSON，需要二次解析。

于是系统设计从“不确定能不能做”变成：

- 主路径：调用官方导出，轮询长任务，拿飞书 Sheet URL。
- 备用路径：分页拉 `demander_get_challenge_item_list`，规范化 JSON 后自己写飞书。

这个阶段的核心是证据驱动。接口是否可行、字段在哪里、状态码怎么表示、失败原因是什么，都来自日志，而不是从页面表现反推。

## 阶段三：用最小 Rust/Salvo 工具验证闭环

在确认接口链路之后，先写了一个小工具，而不是马上做完整系统。

这个小工具只需要三个接口：

- 一个接口接收星图登录态。
- 一个接口手动触发指定星图任务导出。
- 一个接口检查当前登录态是否失效。

这样可以快速验证：

- Rust 服务能否复现浏览器里的星图请求。
- Cookie、CSRF、session_key、User-Agent 是否足以维持会话。
- 指定任务 ID 能否导出到飞书表格链接。
- 登录态失效时后端能否识别。

这一步降低了后续系统化开发的风险。它不是最终形态，但它把“可自动化”从日志分析推进到可运行服务。

## 阶段四：用浏览器插件解决稳定登录态

星图鉴权不是一个简单 token。真实请求依赖：

- Cookie。
- `X-CSRFToken`。
- `session_key`。
- User-Agent。
- 某些接口还可能依赖 `Agw-Js-Conv`、`x-login-source` 等请求头。

所以项目没有选择在后端“凭空登录”，而是做配套浏览器插件：

- 从当前登录的 `xingtu.cn` 页面读取 Cookie。
- 尝试从 Cookie、Storage、页面信息中提取 CSRF 和 session_key。
- 支持手动覆盖。
- 支持向后端上报登录态。
- 支持每 3 小时自动同步一次，但只有用户已经打开 `xingtu.cn` 标签页时才同步。
- 支持导出 `.env`，方便调试期让服务启动时注入登录态。

这是一个很典型的工程化折中：不直接对抗 SSO、验证码和风控，而是把浏览器中的有效登录态安全地转交给后端使用。

## 阶段五：把 006 初版同步整理成模块化 Pipeline

后端主项目一开始从 006 的视频同步试验推进。

最早的 006 已经能完成视频同步，但它更像一次性脚本。后续逐步整理成可迁移、可扩展的 pipeline：

- 抽出直播和视频两条同步流程。
- 把每期活动会变化的配置提出来。
- 保留固定的唯一键逻辑。
- 支持 `bitable_url`、`spreadsheet_url`、`main_table_id`、`audit_table_id` 等活动级配置变动。
- 支持多期活动用 `Vec` 配置循环执行。
- 支持手动登记数据和星图数据合并。
- 支持数据来源字段：`星图数据`、`手动登记`。
- 同一稿件同时存在星图和手动登记数据时优先使用星图，手动登记只补充星图中不存在的稿件。
- 手动登记数据自动写入审核结果 `审核通过`。

这里的设计重点是把“每期活动变化的东西”从流程代码里剥离出去。后面活动换表、换任务、换审核表时，不需要改 pipeline 逻辑。

## 阶段六：从同步飞书表，升级为先入数据库

随着需求变复杂，只同步到飞书多维表已经不够。

项目进一步引入 PostgreSQL 和 SQLx，把同步流程改成：

1. 从星图导出拿飞书 Sheet URL。
2. 从 Sheet 读取星图数据。
3. 从多维表手动登记表读取人工补充数据。
4. 合并两类数据。
5. 先写入数据库结构化表。
6. 再同步到业务多维表。

数据库设计逐步包括：

- 活动期次配置。
- 内容配置，区分直播和视频。
- 星图项目账号。
- 登录态记录。
- 飞书来源记录。
- 视频基础表。
- 视频每日指标追踪表。
- 视频导入历史表。
- 直播场次表。

其中一个关键判断是：只有视频需要追踪每日指标，直播不需要追踪，只保留最新场次数据。

这个阶段把系统从“表格同步工具”升级成“有状态的数据系统”。数据库成为补偿、查询、分析、审计和后续后台集成的中心。

## 阶段七：把工作流产品化

业务流程被整理成几条明确工作流：

- 周期工作流：固定在 03:00、15:00、21:00 拉取数据、导入 pending、同步数据，不通知审核。
- 每日早工作流：固定在 09:00 拉取数据、导入 pending、同步数据、通知审核。
- 每日晚工作流：固定在 23:59 拉取，作为每日最终数据；飞书表同步完成后，将审核表中已填写的审核结果回写数据库，并按稿件 ID 与日期规整项目视频每日新增播放量宽表。
- 登录态巡检：从 00:30 开始每小时检查一次星图登录态，失效时给项目群发通知。

每日早工作流定在 09:00，是为了服务审核场景；每日晚工作流用于沉淀当天最终追踪数据。

这里还确定了业务日期口径：以数据拉取开始时间判断追踪数据属于哪一天，并按 `Asia/Shanghai` 处理业务时间。

工程化价值在于：工作流不再是人工临时执行的脚本，而是可以由服务内置调度器或未来企业后端调度器触发的稳定任务。

## 阶段八：审核通知和运营闭环

同步数据只是前半段，审核提醒是业务闭环。

项目接入飞书 IM 卡片通知，并且按照真实卡片模板变量实现：

- `auditor_ids`：审核人员 ID，逗号分隔。
- `audit_info`：待审核期次信息。
- `video_nums`、`live_nums`：待审核数量。
- `audit_table_url`：直接传入 Markdown 链接。

审核人后来从单期期次配置上移到项目级配置，由 `xingtu_project_auditor` 按 `project + is_active` 生成 `auditor_ids`，不再回退旧活动审核人或账号 `ops_ids`。这样同一个项目新增活动期次时不用重复维护 @ 名单；禁用某个审核人时，也只需要在项目审核人配置里关闭一次，后续活动配置更新不会将其重新启用。

通知前会读取配置好的审核表，统计审核结果为空的数量。如果某一期没有待审核内容，就不进入卡片参数，避免通知里出现无意义期次。

这体现了一个重要原则：通知不是“流程结束时一定发”，而是基于当前待办状态发。这样审核群收到的是可行动信息，而不是噪音。

## 阶段九：服务化为 Salvo 项目

当 pipeline、数据库和工作流都稳定后，项目落地成 Salvo 服务。

服务接口覆盖：

- 健康检查。
- 星图登录态接收。
- 星图登录态检查。
- 手动执行每日早、周期、每日晚工作流。
- 手动将审核表结果同步回数据库。
- pending 来源补偿导入。
- 配置查询。
- 数据查询。
- 视频/直播分析查询。

后续又接入 Salvo 官方 OpenAPI：

- `GET /api-doc/openapi.json`
- `GET /swagger-ui`

这一步让系统从“能跑”变成“能被别人调用、理解和集成”。

## 阶段十：补齐查询和分析能力

为了支持前端展示和运营后台，项目补了分析接口：

- 查询视频基础数据 + metrics 时间序列。
- 展示每个视频的每日增量。
- 汇总所有视频的播放量、点赞量、评论量、稿件数量、作者数量。
- 汇总所有直播的观看人次、ACU 平均值、直播场次数量、主播数量。
- 查询播放量增长最快的前 N 条内容。

视频指标按 `video_daily_metric` 的日期序列计算，并用窗口函数 `LAG` 计算每日增量，避免直接累加多日快照导致重复计算。

这一步说明系统已经从“同步业务表”进一步变成“可分析的数据服务”。

## 阶段十一：容器化和发布

最后项目完成 Docker 化，并针对实际部署环境做了架构处理：

- 本地是 M1 Darwin arm64。
- 服务器是 Linux amd64。
- 因此使用 `docker buildx build --platform linux/amd64 --push` 构建。
- 镜像发布到 Docker Hub：`trihlp/lark-utils-exp`。
- 发布 tag 包括 `latest` 和日期架构 tag。

同时补了 Docker 部署文档，明确必填环境变量：

- `DATABASE_URL`
- `LARK_APP_ID`
- `LARK_APP_SECRET`

以及可选调试登录态变量：

- `XINGTU_ACCOUNT_ID`
- `XINGTU_COOKIE`
- `XINGTU_CSRF_TOKEN`
- `XINGTU_SESSION_KEY`
- `XINGTU_USER_AGENT`

这一步把项目从本地开发状态推到了可部署、可运维状态。

## 工程化方法总结

### 1. 先解决最大未知数

最开始最大未知数不是 Rust 怎么写，也不是飞书怎么同步，而是星图页面到底怎么请求数据。你先做插件采集器，把不可见行为变成日志，这是后续所有判断的基础。

### 2. 用 MVP 验证链路，而不是一次性造完整系统

在确认接口后，先写小 Salvo 工具验证任务 ID 到飞书链接。这让“能不能自动化”先闭环，再把精力投入数据库、定时任务、通知和部署。

### 3. 把不稳定输入显式配置化

每期活动的表格、表 ID、任务 ID、审核表、通知人都会变。项目没有把这些写死在流程里，而是逐步抽成 JSON 和数据库配置。

### 4. 把外部平台风险变成系统能力

星图登录态不稳定、导出可能受 IP 策略影响、飞书 API 响应可能不完整。这些风险没有被忽略，而是变成：

- 登录态上报接口。
- 登录态巡检。
- pending 补偿导入。
- 官方导出主链路和分页拉取备用链路。
- 错误上下文和文档。

### 5. 数据先结构化，再同步和分析

先入库再同步，让系统拥有自己的事实来源。飞书表格是业务协作界面，数据库是系统状态和分析基础。

### 6. 每一步都留下交接材料

项目过程中持续补充了：

- 调试日志阅读指南。
- 插件 README。
- HTTP API 文档。
- Docker 部署文档。
- OpenAPI/Swagger。

这让后续 AI、新同事或企业后端接入时，不需要重新猜系统设计。

## 当前项目成果

截至目前，项目已经具备：

- 浏览器插件采集调试信息、上报星图登录态、导出 `.env`。
- 星图任务导出飞书 Sheet URL。
- 直播/视频同步 pipeline。
- 手动登记数据合并。
- 视频每日追踪入库。
- pending 来源补偿导入。
- 每日早、周期同步、每日晚工作流。
- 登录态巡检和失效通知。
- 审核通知卡片。
- PostgreSQL + SQLx 数据层。
- Salvo HTTP 服务。
- 查询和分析 API。
- Swagger/OpenAPI 文档。
- Docker linux/amd64 镜像发布。

这套系统已经从“人工打开网页下载表格”演进成“可调度、可补偿、可查询、可部署的自动化工作流服务”。

## 后续演进方向

后续可以继续沿着这几个方向增强：

- 接入企业后端账号体系和权限校验。
- 把活动配置管理做成后台页面。
- 对星图登录态做加密存储或接入密钥系统。
- 将官方导出和分页 JSON 两条链路统一成可切换策略。
- 给工作流执行记录增加可视化状态页。
- 对分析接口增加更多维度，如活动期次、内容类型、作者分组、趋势对比。
- 对飞书 wiki 表格点击采集继续逆向，支持更精确读取鼠标所在单元格数据。

## 一句话总结

这个项目的推进方式，是从真实行为观测开始，用日志验证接口，用 MVP 验证链路，再把配置、数据、工作流、通知、查询、文档和部署逐层工程化，最终把一个重复人工操作变成可运营的自动化系统。
